
• 有，基于现在已经拆出来的 host services，我建议按这几个方向继续收紧：

  1. 保留 HostService 作为 root/shared state
     现在 HostService 适合只放：
      - dbcl
      - 全局 scope/job
      - constants
      - shutdown/init
      - 少量跨服务共享状态，比如 skipWorldSizeUpdate

     不建议再往里面放业务函数。以后新增 host 功能，默认先放到具体子服务。
  2. 已拆服务的边界基本合理
     当前这些职责是清楚的：
      - HostQueryService: 查询、列表、VO组装(read model)
      - HostInstallService: 创建、安装、启动准备(create/install/startup preparation)
      - HostControlService: start/stop/restart/command/status/control
      - HostRuntimeService: websocket session、playable channel、runtime state
      - HostPresenceService: 在线玩家、idle monitor、global player list
      - HostModsService: extra/disabled mods
      - HostConfigService: config 文件读写
      - HostFileService: 普通文件管理
      - HostMemberService: 成员/权限角色 mutation
      - HostRoute: routing only
  3. 避免服务之间互相绕成环
     现在最需要注意的是 dependency direction：
      - route 可以依赖所有 service
      - feature service 可以依赖 HostQueryService
      - feature service 可以依赖 HostService.dbcl/constants
      - 尽量避免 HostQueryService 依赖太多 mutation service
      - 尽量避免 HostControlService 和 HostRuntimeService 双向互调过多

     如果两个 service 开始互相调用很多，说明它们边界可能错了，或者需要抽一个更底层 helper。
  4. object 可以继续用，但别把类型定义塞进 object
     对当前这种 Ktor/Mongo 单例服务，object XxxService 可以接受，和现有风格一致。

     但建议：
      - DTO/data class 放 object 外面
      - extension properties/functions 如果是跨服务共用，也放 object 外面或专门 service
      - 只给服务内部用的 helper 可以留在 object 内 private/internal
  5. 下一批最值得抽
     优先级我会这样排：
      - HostLifecycleService: delete/changeVersion/changeOptions
      - HostContainerService: makeContainer/containerEnv/OverlaySources
      - HostLogService: listenLogs/sendLatestLogTail
      - HostAccessService: HostContext/needAdmin/hostContext
  6. 命名建议
     继续按“动作域(domain action)”命名，不要太泛：
      - 好：HostModsService, HostConfigService, HostInstallService
      - 一般：HostUtilService, HostCommonService, HostManager
      - 避免：HostHelper, HostMisc

  总体看，现在拆分方向是健康的。接下来关键不是继续无限细拆，而是把 HostService 压到“共享根对象(root
  holder)”的位置，然后让每个子服务只管一个明确业务面。
